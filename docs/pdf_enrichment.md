# Автоматическое дополнение из даташитов

Проект готовит список пустых полей, принимает результаты внешнего обработчика и записывает прошедшие проверку значения в SQLite. Внешний обработчик читает PDF и извлекает значения. Выбор модели, OCR, поиска по документам и способа разбора таблиц остаётся за разработчиком обработчика.

```text
Сохранённый сбор с PDF
  → prepare → tasks.jsonl
  → внешний обработчик → candidates.jsonl
  → apply + approved-rules.json → preview.jsonl
  → apply --commit + те же входные файлы → SQLite и applied.jsonl
```

## Подготовка сбора

Команды запускаются из корня проекта, откуда загружаются матрица аналитиков и правила сопоставления каталога. Во всех примерах `--output data/yageo/runs/aluminum` указывает на **папку существующего сбора** с файлом `crawl_state.sqlite3`. Если у сбора другое имя, в командах нужно указать его фактический путь.

Если PDF ещё не скачаны, для этого сбора можно запустить обычную загрузку.

```bash
uv run python -m ekb_parser datasheets --output data/yageo/runs/aluminum
```

Загрузчик сохраняет PDF в папку `datasheets/` внутри сбора и регистрирует их в SQLite. Случайно положенный в папку PDF без записи о скачивании в SQLite в очередь не попадёт.

## 1. Сформировать очередь полей

```bash
uv run python -m ekb_parser pdf-enrichment prepare \
  --output data/yageo/runs/aluminum \
  --tasks tasks.jsonl
```

`prepare` читает сохранённые компоненты, уже внесённые дополнения и текущую матрицу. В очередь попадает поле, если одновременно выполняются три условия.

- Компонент отнесён к группе с настроенными требованиями.
- Поле обязательное и ещё пустое. Заполненные значения из каталога, матрицы или дополнений пропускаются.
- Даташит зарегистрирован как скачанный, доступен в папке сбора и его SHA-256 совпадает с записанным в SQLite.

`--tasks` задаёт путь к новому JSONL-файлу. Каждая строка соответствует одному полю одного артикула. SQLite открывается на чтение. Команда печатает счётчик, например `{"tasks": 240}`. Ноль задач означает, что ни одно поле не прошло условия отбора. Для запуска по одному полю можно добавить `--field "Номинальное напряжение, В"`. Имя должно точно совпадать с матрицей.

Пример одной задачи с условным артикулом и хешем. Здесь JSON отформатирован для чтения, в JSONL каждая запись занимает одну строку.

```json
{
  "version": 1,
  "target": {
    "source": "yageo",
    "source_id": "123",
    "part_number": "TEST-16",
    "group": ["Конденсаторы", "Конденсаторы оксидно-электролитические"],
    "field": "Номинальное напряжение, В",
    "document_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "manufacturer": "TEST",
  "series": "TEST",
  "pdf_path": "datasheets/example.pdf",
  "pdf_url": "https://example.com/datasheet"
}
```

`source_id` — идентификатор записи у источника, `part_number` — артикул для поиска в PDF. В `target.group` первым идёт название листа матрицы, вторым — название группы. `pdf_path` отсчитывается от папки сбора из `--output`. `pdf_url` хранит ссылку на оригинал.

## 2. Обработать PDF и подготовить кандидатов

Внешний обработчик читает `tasks.jsonl` и создаёт `candidates.jsonl`. Чтобы разобрать общий даташит один раз, задачи можно сгруппировать по `target.document_sha256`. При работе с таблицей нужно сопоставить артикул со строкой, учесть заголовки и применимые сноски. Общее значение серии подходит, если паспорт распространяет его на нужный артикул.

В кандидата нужно перенести объект `target` из задачи целиком. `value` передаётся в единицах поля матрицы. В `evidence` указывается физический номер страницы PDF с единицы и фрагмент, подтверждающий значение. В необязательном `conditions` можно сохранить условия измерения, например температуру и частоту. Если значение отсутствует или неоднозначно, обработчик может пропустить задачу или записать причину в собственный журнал.

```json
{
  "version": 1,
  "target": {
    "source": "yageo",
    "source_id": "123",
    "part_number": "TEST-16",
    "group": ["Конденсаторы", "Конденсаторы оксидно-электролитические"],
    "field": "Номинальное напряжение, В",
    "document_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "rule_id": "example:aluminum_rated_voltage@1",
  "value": 16,
  "evidence": {"page": 5, "quote": "TEST-16  16 VDC"}
}
```

`rule_id` связывает результат с правилом извлечения. Например, правило может описывать поиск артикула в определённой таблице и чтение столбца номинального напряжения. Его можно проверить один раз и использовать для всех подходящих строк.

Машиночитаемые контракты для проверки формата доступны командой `uv run python -m ekb_parser pdf-enrichment schema`. Она выводит схемы `task`, `candidate` и `approved_rules`.

## 3. Указать одобренные правила

`approved-rules.json` — отдельный JSON-массив, который ведёт команда. После проверки правила в файл нужно добавить его идентификатор с версией, источник, группу и поле. Если одобрение распространяется на конкретный даташит, в запись нужно включить `document_sha256`. Правило без этого ключа подходит для любого PDF в указанной области. В таком случае обработчик должен сам подтвердить, что документ соответствует проверенному шаблону. При изменении логики правила нужен новый `rule_id`. Пустой список одобрений записывается как `[]`.

```json
[
  {
    "version": 1,
    "rule_id": "example:aluminum_rated_voltage@1",
    "source": "yageo",
    "group": ["Конденсаторы", "Конденсаторы оксидно-электролитические"],
    "field": "Номинальное напряжение, В",
    "document_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
]
```

На этапе одобрения нужно сверить смысл поля, единицы и условия. Например, паспортный ток компонента и рабочий ток в конкретной схеме требуют разных оснований. Проверка содержимого цитаты на указанной странице и правильности преобразования единиц относится к обработчику и проверке правила.

## 4. Проверить пакет перед записью

```bash
uv run python -m ekb_parser pdf-enrichment apply \
  --output data/yageo/runs/aluminum \
  --input candidates.jsonl --approved-rules approved-rules.json \
  --report preview.jsonl
```

`apply` без `--commit` читает SQLite и проверяет каждую строку кандидатов. Проект сверяет артикул и группу, проверяет наличие и SHA-256 текущего PDF, проверяет, что поле по-прежнему обязательное и пустое, и ищет подходящее одобрение. Полные дубли обрабатываются один раз. Если на одно поле пришли разные кандидаты, запись этого поля блокируется.

В `preview.jsonl` указываются номер строки входного файла, статус и данные кандидата. Для некорректной строки указывается причина ошибки. Готовые к записи строки получают статус `ready`. SQLite остаётся без изменений.

## 5. Записать прошедшие проверку значения

```bash
uv run python -m ekb_parser pdf-enrichment apply \
  --output data/yageo/runs/aluminum \
  --input candidates.jsonl --approved-rules approved-rules.json \
  --report applied.jsonl --commit
```

С `--commit` команда заново читает `candidates.jsonl` и `approved-rules.json` и повторяет проверки по текущему состоянию сбора. Поэтому значение, которое появилось в поле между предпросмотром и записью, сохраняется. Отчёт предпросмотра служит для проверки и не передаётся на вход записи.

Прошедшие проверку значения записываются в таблицу `component_supplements` и получают статус `applied`. Вместе со значением сохраняются ссылка на PDF, номер страницы, цитата, SHA-256, идентификатор правила и условия, если они переданы. Дополнения учитываются в карточках компонентов и статистике заполненности.

## Как читать отчёты

Обе команды `apply` печатают счётчики в JSON. Успешное завершение допускает пропуски, поэтому для автоматизации нужно учитывать статусы в отчёте. Файлы очереди и отчёта создаются по новому пути. Для повторного прогона нужен новый путь отчёта.

| Статус | Что произошло |
| --- | --- |
| `ready` | Кандидат прошёл предпросмотр. |
| `applied` | Значение записано в SQLite. |
| `already_filled` | В поле уже есть значение. Повторный импорт его пропускает. |
| `rule_not_approved` | Для кандидата нет одобрения с нужной областью действия. |
| `conflict` | На одно поле пришли разные кандидаты. Поле пропущено. |
| `duplicate` | Строка полностью дублирует другого кандидата. |
| `component_missing` | Компонент с таким идентификатором отсутствует в этом сборе. |
| `target_changed` | Текущий артикул или группа отличается от указанной в задаче. |
| `pdf_changed_or_missing` | PDF недоступен или его хеш отличается от указанного в задаче. |
| `field_unavailable` | Поле больше недоступно для заполнения по текущим требованиям. |
| `invalid` | Строка не соответствует формату кандидата. |
